# 2026-02-24: <APP_NAME>-env-secret
## Secret Resource Standardization (`kind: ExternalSecret` `spec.target`)
This convention specifically governs the spec.target.name field within the ExternalSecret custom resource.
While the `metadata.name` identifies the ESO "instruction" in the cluster, the `spec.target.name` defines the actual Kubernetes Secret object that is generated.
By standardizing this target name, it is ensured that the application's Deployment or Pod spec can consistently reference its environment variables using a predictable naming scheme.

```yaml 
apiVersion: external-secret.io/v1beta1
kind: ExternalSecret
metadata:
  name: linkding-es              # The ESO Instruction name
spec:
  target:
    name: linkding-env-secret   # <--- THIS is the standardized target name
    creationPolicy: Owner
  data:
    - secretKey: LD_DATABASE_URL
      remoteRef:
        key: apps/production/linkding
        property: db_url
```
## The Problem: Bespoke Resource Naming

Initial implementations utilized highly specific names for Kubernetes Secret targets (e.g., `blocky-auth-credentials`). This approach introduced significant cognitive overhead and prevented the creation of standardized automation. In a bespoke naming environment, identifying which secret provides environment configuration for a given pod requires a manual inspection of the `deployment.yaml` and `external-secret.yaml` manifests. This lack of predictability increases the risk of configuration errors during refactoring and complicates the logic required for cluster-wide auditing scripts.

## The Solution: Functional Suffix Pattern

To ensure predictability across the cluster, all secrets generated by the External Secrets Operator (ESO) must follow a functional suffix pattern based on the application name.

Pattern: `<APP_NAME>-env-secret`

Example: `blocky-env-secret`, `linkding-env-secret`

This naming convention abstracts the content of the secret (which may change) and focuses on its function (injecting configuration into the environment). By standardizing the target name, the `envFrom` field in Kubernetes Deployments becomes predictable, allowing for the creation of reusable application templates.

# 2026-05-25: Observability Domain Standardization (VictoriaMetrics)

## The Problem: Naming Redundancy and Selector Mismatches

Initial observability configurations introduced unnecessary namespace clutter by applying the cluster prefix to core system runtimes (e.g., `name: athanor-agent`). Concurrently, tracking labels utilized values that failed to mirror the underlying infrastructure resources (e.g., matching against `metrics-agent` while the deployment was named `vmagent`). This created an architectural mismatch, increased cognitive load when navigating directories via `snacks.explorer`, and deviated from upstream patterns.

## The Solution: Component Isolation and Intent-Based Matching

To maintain architectural symmetry, all custom resources within the VictoriaMetrics monitoring stream must be named strictly after their explicit microservice engine function. No cluster prefixes are permitted.

|**Target**|**Why it is relevant**|**Senior Audit Question**|
|---|---|---|
|**`VMAgent`**|`vmagent`|Namespace-scoped. Collects global cluster telemetry.|
|**`VMAlertmanager`**|`vmalertmanager`|Namespace-scoped. Preserves predictable local cluster DNS profiles.|
|**`VMServiceScrape`**|`<app>-scrape`|Namespace-scoped. Standardized target discovery matching upstream norms.|
|**`VMPodScrape`**|`<app>-pod-scrape`|Namespace-scoped. Isolates raw pod scraping endpoints from services.|Go


### Global Ingestion Contract

For the centralized `vmagent` daemon to recognize and integrate distributed scrapers into its runtime engine, all `VMServiceScrape` and `VMPodScrape` resources must feature the standardized intent-based label key and value pairing:o
```yaml
metadata:
  labels:
    athanor.io/scrape: "true"
```

## Learning: Predictability as a Feature

In a "Senior" infrastructure architecture, predictability is not a preference; it is a primary feature of the system. Transitioning from "Snowflake" (unique) configurations to standardized patterns allows the infrastructure to scale without a corresponding increase in management complexity. This methodology aligns with Twelve-Factor App (Factor III) principles by treating the environment as a consistent interface for secret injection, regardless of the specific application logic.

## secret resources taxonomy
|**Suffix Pattern**|**Use Case**|**Implementation Pattern**|
|---|---|---|
|**`<app>-env-secret`**|Flat key-value pairs injected directly into the application container environment blocks.|Used via `envFrom` references inside deployments.|
|**`<app>-file-secret`**|Sensitive files (e.g., configuration profiles, `.dockercfg`) that must be mounted securely into container paths.|Mounted explicitly using the deployment `volumes` specification.|
|**`<app>-tls-secret`**|Cryptographic certificates and private keys used for internal cluster mTLS communication channels.|Managed cleanly by ingestion proxies and gateways.|
