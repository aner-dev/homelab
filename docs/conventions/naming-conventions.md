# 2026-02-24: <APP_NAME>-env-secrets
## Secret Resource Standardization (ExternalSecret Targets)
## The Problem: Bespoke Resource Naming
Initial implementations utilized highly specific names for Kubernetes Secret targets (e.g., blocky-auth-credentials). This approach introduced significant cognitive overhead and prevented the creation of standardized automation.
In a bespoke naming environment, identifying which secret provides environment configuration for a given pod requires a manual inspection of the deployment.yaml and external-secret.yaml manifests.
This lack of predictability increases the risk of configuration errors during refactoring and complicates the logic required for cluster-wide auditing scripts.

## The Solution: Functional Suffix Pattern
To ensure predictability across the cluster, all secrets generated by the External Secrets Operator (ESO) must follow a functional suffix pattern based on the application name.

Pattern: <APP_NAME>-env-secrets

Example: `blocky-env-secrets`, `linkding-env-secrets` 

This naming convention abstracts the content of the secret (which may change) and focuses on its function (injecting configuration into the environment).
By standardizing the target name, the envFrom field in Kubernetes Deployments becomes predictable, allowing for the creation of reusable application templates.

## Learning: Predictability as a Feature
In a "Senior" infrastructure architecture, predictability is not a preference; it is a primary feature of the system.
Transitioning from "Snowflake" (unique) configurations to standardized patterns allows the infrastructure to scale without a corresponding increase in management complexity.
This methodology aligns with Twelve-Factor App (Factor III) principles by treating the environment as a consistent interface for secret injection, regardless of the specific application logic.
